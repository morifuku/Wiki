📙 CUPSの方向性¶

2026/11/26公開 2026/11/26更新

  • 質問者: Shigeru Morifuku

  • 回答者: Claude Opus 5.5

  • 回答日: 2026/11/26

  • 免責: 回答者は AI であり、間違えることがあります。

🟩 Q: 4GでのPGWのCUPS化のインターフェース仕様はエレガントではなかった。5Gもそのまま。この先どうなるの？¶

結論から言うと、「エレガントではない」という評価は業界内でもよく聞きますし、私もかなり当たっていると思います。ただ、そうなったのにははっきりした理由があります。

🟨 4G CUPS（Sx/PFCP）がエレガントでない点¶

1. 汎用の転送抽象ではなく、GW の中身を切っただけ
CT4 は OpenFlow などを採らず、UDP/IP 上の TLV エンコードによる 3GPP 独自プロトコル PFCP を定義した経緯があります。設計方針はCP が Sx セッションにルール群をプロビジョニングして UP の処理を制御するというもので、中身は「GTP-C っぽいセッション制御プロトコル」です。OpenFlow や P4Runtime のような「match/action を一般化した API」にはなっていません。

2. 後方互換が最優先の制約だった
既存の SGW/PGW を、つながっている既存ノードに影響を与えずに分離型ノードへ置き換えられることが要件でした。つまり外から見れば箱は1つのままで、その内部を割ってメッセージ化した形です。GTP トンネルやベアラ、Gx/Gy の課金モデルといった EPC の前提がそのまま PFCP の情報要素に写し込まれています。

3. ルールモデルが重く、UP に状態が集まる
PDR/FAR/QER/URR/BAR が ID で互いにリンクし合い、そこに precedence と usage reporting が絡むので、UP はセッションごとの状態を大量に抱えます。CP は UP を細かく管理し続けることになります。Linux カーネルへの PFCP 取り込みが議論されたときも、netdev 側からPFCP はかなり複雑なプロトコルだという反応が出ていました。

4. マルチベンダ相互接続が実際には難しい
predefined rule（名前だけを参照し、中身は UP 側の設定に任せる）やベンダ拡張 IE に頼ることが多いです。そのため「CP と UP を別ベンダで組める」という CUPS の売りは、商用ではあまり実現していない印象です。

🟨 5G でもそのままの理由¶

N4 は Sx と同じ PFCP で、5G 向けの拡張（QoS Flow、ULCL/BP、ATSSS、TSN など）が足されただけです。TS 29.244 で規定され、5GC の主要プロトコルでありながら 4G EPC の CUPS にも使われている状態です。5GC は SBA（HTTP/2 + JSON）で統一されましたが、N4 は SBI にならずに残りました。理由は主に次の2つです。

  • UPF はパケット処理の箱なので、REST 的なリクエスト/レスポンスでは遅延の面でもモデルの面でも合わない。

  • 4G CUPS の実装資産をそのまま流用できる。

Rel-16 では GTP-U に代わる UP プロトコル（SRv6 など）も検討されましたが、結局 GTP-U 維持で落ち着きました。さらに PFCP はBroadBand Forum の TR-459 で定義された分離型 BNG の CP/UP 間インタフェースにも使われています。モバイル以外にも広がったことで、置き換えはますます難しくなりました。

🟨 この先（6G）¶

6G では、UP 周りを見直す動きがはっきり出ています。

  • 3GPP CT4：Rel-20 向けに「6G の UP 管理とプロトコルの検討（FS_6G_UPM）」が提案されています。既存の UP プロトコル（GTP-U）の限界を調べ、拡張または置き換えの可能性を検討することと、UP アーキテクチャ拡張に向けたパケット処理と QoS 制御の改良が作業項目に入っています。

  • SA2：6G アーキテクチャの文書 TR 23.801 で、より多様なアプリケーションとトラフィックパターンに対応する UP アーキテクチャの改善が目標に掲げられています。

  • IETF（dmm WG）：SRv6 MUP 系のドラフトが続いています。2024年版では3GPP のアーキテクチャとシグナリングを変えずに一部ベンダ・事業者が推す代替 UP 実装や、6G での UPF とアクセスノードの統合が論じられていました。2026年7月版は6G のマルチベンダ相互接続性、UPF 分散による柔軟性、スケーラビリティと耐障害性を扱っています。

  • 時期：Rel-20 の WG スタディは 2027年6月に終わる予定なので、方向が決まるのはまだ先です。

🟨 私の見立て（予測です）¶

  • GTP-U：今回は本気で議論されると思います。それでも全面的に置き換わるより、「GTP-U 継続＋SRv6 などをオプションで許す」という折衷になる可能性が高いと見ています。Rel-16 でも同じ結論でした。

  • N4/PFCP：消えるより「6G 版 PFCP」として整理・拡張される可能性が高いと思います。SBI 化（UPF を普通の NF にする）案も出るでしょうが、遅延とセッション状態の扱いがネックです。

  • 本当に変わるとしたら：UPF と RAN（CU-UP）の統合や、UP の中身を P4 的に記述するモデルでしょう。ただ、事業者が持つ課金・LI・運用の資産が重く、3GPP がそこまで踏み込むかは五分五分以下だと思います。

要するに CUPS は、技術的なエレガンスより移行性を選んだ設計で、5G はその負債を引き継ぎました。6G はそれを返すかどうかを議論している段階です。ただ、これまでの3GPPのやり方を見る限り、返さずに借り換えるだけで終わる可能性も十分あります。

🟩 Q: 「UPF と RAN（CU-UP）の統合」は、基地局からN6が出ていくかんじ？¶

はい、だいたいそういうイメージです。ただし「基地局」が指す場所には少し注意が必要です。

🟨 何がくっつくのか¶

今の 5G の UP 経路はこうなっています。

UE ─(無線)─ DU ─(F1-U)─ CU-UP ─(N3: GTP-U)─ UPF ─(N6)─ DN

CU-UP（PDCP/SDAP）と UPF を1つの機能にまとめると、こうなります。

UE ─(無線)─ DU ─(F1-U)─ [CU-UP + UPF] ─(N6)─ DN

N3 の GTP-U トンネルは内部に吸収されて消え、その場所から直接 N6 が出ていきます。前回挙げた IETF のドラフトも、6G のモバイルネットワークで UPF とアクセスノード（AN）を統合する可能性を論点の1つにしています。

🟨 「基地局から」の意味¶

CU-UP は、アンテナが立っている局舎（DU やセルサイト）ではなく、少し集約した地域局舎やエッジ DC に置かれることが多いです。なので現実的には「セルサイトから N6」より「CU を集約しているエッジ拠点から N6」になります。セルサイトまで下ろす形も可能ですが、構成としては極端な部類です。

🟨 うれしい点¶

  • GTP-U のホップが1つ減る：トンネルの終端と再カプセル化、N3 の転送網がいらなくなり、遅延も装置も減ります。

  • QoS の二重管理がなくなる：今は UPF が QFI を付け、SDAP が QFI を DRB に割り当てる、という2段構えです。統合すれば1か所で済みます。

  • ローカルブレイクアウトが標準の形になる：4G の LIPA/SIPTO や、5G の ULCL＋MEC でやってきたことを、例外ではなく基本構成にできます。

🟨 難しい点（ここが本題）¶

  • アンカーの問題：UE の IP アドレスを払い出し、N6 側に経路を広告する拠点（PSA）がエッジにあると、ハンドオーバーで CU が変わるたびにアンカーも動きます。そうすると IP の継続性が崩れます。

    • 5G の SSC mode 2/3（アンカーの付け替え）で逃げる

    • アンカーは中央に残し、エッジからは N9 で中央へ戻す（統合のうまみが半減します）

    • SRv6 MUP のように、アンカーという考え方そのものをルーティング（BGP で UE プレフィックスを広告する等）に置き換える

    だいたいこの3つの考え方に分かれます。6G の議論の中心もここです。

  • 課金・LI・ポリシー：URR による従量計測や合法的傍受の装置を、多数のエッジに分散配置することになります。運用面でもセキュリティ面でも重いです。

  • ベンダ境界：RAN ベンダとコアベンダの境目が UPF の中に食い込むことになります。商売上の抵抗はかなり大きいはずです。

🟨 まとめ¶

「基地局（CU 拠点）から N6 が直接出る」で合っています。ただ技術的な焦点は、統合そのものより「IP アンカーをどこに置き、移動をどう扱うか」です。GTP トンネルとアンカーという前提を捨てるのか、残したまま箱だけまとめるのかで、6G の UP の姿はかなり変わってくると思います。

🟩 スムーズなハンドオーバが必要なのは、通話サービスだけ？¶

かなりの部分はその通りだと思います。ただ「通話だけ」と言い切るには例外がいくつかあります。それと、話を2つに分けたほうが整理しやすいです。

🟨 「ハンドオーバ」の中身は2層ある¶

  1. RAN 内の HO：セルが変わる間にパケットを落とさないこと。これは CU-UP と UPF を統合しても、Xn 経由のデータ転送などでこれまで通り実現できます。

  2. IP アンカーの移動：UE の IP アドレスが変わること。統合で問題になるのはこちらです。

なので論点は「IP アドレスが変わって困るのはどのアプリか」になります。

🟨 IP アドレスが変わっても平気なもの（大半）¶

  • Web/HTTP：短い接続の繰り返しなので、つなぎ直せば済みます。

  • QUIC/HTTP3：Connection ID があるので、コネクションをそのまま移行できます。

  • 動画視聴（HLS/DASH）：バッファがあるので、セグメント1つ取り直せば済みます。

  • SNS やメッセンジャー：アプリ側で再接続するのが前提の作りです。

スマホのアプリは Wi-Fi とモバイル回線の切り替えに日常的にさらされているので、IP アドレスが変わることを前提に作られています。その意味で「普通のデータ通信はシームレスでなくてもいい」というご指摘は正しいです。

🟨 通話以外で困るもの¶

  • リアルタイム系：ビデオ会議（WebRTC は ICE restart で戻りますが、数百 ms〜秒単位で途切れます）、クラウドゲーム、ライブ配信のアップロード。

  • 長時間張りっぱなしのセッション：SSH、IPsec/企業 VPN（MOBIKE がなければ張り直し）、IP アドレスで ACL を書いている業務システム。

  • 産業・車載：V2X、遠隔操作、TSN 連携などの URLLC 系。6G が売りにしたい領域ほど IP の継続性が要ります。

  • ネットワーク側の都合：CGNAT やファイアウォールの状態、LI、課金のセッション。

🟨 現実的な落としどころ¶

実はこの切り分けは DNN（APN）単位でできてしまいます。

  • IMS DNN：アンカーを中央に固定（SSC mode 1）。VoNR はここを通るので通話は守られます。

  • internet DNN：エッジで統合 UPF から直接 N6 に出す（SSC mode 2/3）。IP が変わってもアプリ側で何とかしてもらいます。

  • URLLC やエンタープライズ向けの DNN/スライス：用途に応じて中央アンカーか、ルーティングベースの方式を選びます。

つまり「シームレスさが必要なのは通話などの一部だけなので、そこだけ中央アンカーに残し、それ以外はエッジで割り切る」という設計は十分成り立ちます。CU-UP＋UPF 統合を推す側の言い分も、ほぼこの論理です。

残る問題は、通話以外で困るリアルタイム系と産業系が、まさに 6G の売りとして挙げられている領域だという点です。だから標準化の議論が「割り切り」だけで終わらず、アンカーなしで IP の継続性を保つ方式（SRv6 MUP など）に向かっているのだと思います。
