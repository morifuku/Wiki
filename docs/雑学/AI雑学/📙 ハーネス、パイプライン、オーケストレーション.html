📙 ハーネス、パイプライン、オーケストレーション¶

2026/11/19公開 2026/11/19更新

  • 質問者: Shigeru Morifuku

  • 回答者: Claude Opus 5.5

  • 回答日: 2026/11/19

  • 免責: 回答者は AI であり、間違えることがあります。

🟩 Q: ハーネスとはJenkinsのパイプラインみたいなもの？¶

似ている部分はありますが、本質は違います。

似ている点
どちらも「中身（ビルド処理／LLM）を外から包んで、実行・制御・記録する仕組み」です。ジョブを起動する、ログを残す、権限を管理する、といった役割は共通しています。

違う点：流れを決めるのが誰か

  • Jenkins のパイプラインは、人が書いた Jenkinsfile のとおりにステージが進みます。checkout → build → test → deploy のように、手順は事前に決まっています。

  • AIのハーネス（Claude Code などがそうです）は、流れを決めません。決めるのはモデルで、ハーネスは次のループを回すだけです。

    1. モデルにプロンプトと、使えるツールの一覧を渡す

    2. モデルが「このツールをこの引数で呼びたい」と返す

    3. ハーネスがそのツール（bash、ファイル読み書き、検索など）を実際に実行する

    4. 結果をモデルに返して 1 に戻る。モデルが「完了」と言ったら終了

ハーネスが担当するのは、ツールの実装、権限チェック（「この rm を実行してよいか」の確認など）、コンテキストの管理（長くなった履歴の要約・圧縮など）、サンドボックス化、ログ記録です。つまり「何をやるか」はモデル、「それを安全に実行できる環境」はハーネス、という分担です。

C/C++ にたとえると
Jenkins はシェルスクリプトやバッチのような固定手順書です。ハーネスは、外部プロセス（LLM）からのリクエストを受けてシステムコールを代行するイベントループ付きのランタイムに近いです。あるいは、ゲストOS（モデル）の要求を受けて実I/Oを代行・制限するハイパーバイザ、と考えると分かりやすいと思います。

補足：「テストハーネス」との関係
もともと「ハーネス」はテスト分野の用語です。テスト対象をスタブやドライバで包んで、実行・計測する枠組みのことでした。AIの文脈でも「モデルを包んで動かす枠組み」という同じ意味で使われています。

なお、Jenkins のステージの中で Claude Code をヘッドレス実行する、といった組み合わせも普通に行われています。その場合は、外側の固定フローを Jenkins が担当し、その中の判断が必要な部分をハーネスとモデルが担当する、という二層構造になります。

🟩 Q: LLM①で作った脚本をLLM②に食わせて動画を生成する─のような連携は¶

それは「オーケストレーション」と呼ばれる層の話です。ハーネスでもできますし、Jenkins的なワークフローでもできます。どちらを使うかは、「流れが固定か、途中で判断が要るか」で分かれます。

🟨 固定パイプライン型（Jenkins に近い）¶

LLMでプ脚本を作る → シーンごとのプロンプトに分割する → 動画生成モデルに投げる → 結合する、という流れが毎回同じなら、普通のワークフローで十分です。

  • n8n、Dify などのノーコード系ワークフローツール

  • 画像・動画生成なら ComfyUI のノードグラフ

  • あるいは Python やシェルスクリプトで、APIを順番に叩くだけでも可

この型では、各LLMは「関数の1ステップ」として呼ばれるだけです。判断はしません。

🟨 エージェント型（ハーネスが本領を発揮する）¶

「Claudeが脚本を書く → 動画生成APIをツールとして自分で呼ぶ → 出来上がった動画（のフレーム）を見て、気に入らなければプロンプトを直して再生成する」というように、途中の分岐や再試行をモデル自身に判断させたいときです。

このとき動画生成モデルは、ハーネスに登録された「ツールの1つ」になります。登録方法はMCPサーバーとして公開するか、スクリプトをbashから呼べるようにしておくかです。Claude Code 上で「この脚本で3シーン作って、出来を確認して直して」と頼めば、モデルがツール呼び出しを繰り返して進めます。

🟨 実務で多い形：混合¶

  • 外枠は固定パイプライン：脚本生成 → シーン分割 → 生成 → 結合

  • 「生成結果のチェックと再生成」の部分だけエージェントに任せる

こうすると、コストと挙動が読みやすく、品質判断だけ柔軟にできます。前回話した「Jenkins の中で Claude Code を動かす」二層構造と同じ発想です。

🟨 作るときの注意点¶

  • 動画生成は遅くて高い：数十秒〜数分かかり、課金も大きいです。エージェントに無制限に再試行させないよう、回数の上限を設けてください。

  • 非同期API：多くの動画生成APIは「ジョブ投入 → ポーリングで完了待ち」の形式です。ツール側でその待ちを吸収しておくと、モデルが扱いやすくなります。

  • 一貫性：シーン間でキャラクターや画風を揃えるのが一番難しいところです。参照画像やシード、スタイル記述を、パイプライン側で固定して渡す設計にするのが定石です。

🟩 Q: 頭で「パイプラインを想定して」アーキテクチャは「ハーネスで」って、「状態遷移表」が可視化されないままコード書いているみたいで、危なっかしい¶

その感覚は正しいです。エージェント型にすると「状態遷移はモデルの頭の中にあって、外からは見えない」状態になります。状態遷移表のない状態機械を本番に出すのと同じ気持ち悪さです。

実務での対策は「状態遷移はコード側で明示的に持ち、モデルには遷移の中身だけを任せる」です。

1. 状態機械を外に出す

PLOT → SPLIT → GENERATE(scene i) → REVIEW(scene i) ─OK→ 次のシーン → CONCAT → DONE
                      ↑                    │NG（再試行回数 < N）
                      └────────────────────┘
                                           │NG（再試行回数 ≥ N）→ FAILED / 人の判断待ち

これを enum と switch（あるいは遷移表）でコードに書きます。LLMを呼ぶのは「各状態の中の処理」と「REVIEW での OK/NG 判定」だけにします。こうすると遷移図はコードそのものになり、図にも描けます。LangGraph などが「グラフで定義する」方式を取っているのは、まさにこの問題への答えです。

2. モデルの出力を「遷移イベント」に限定する
自由文ではなく、JSONスキーマで出力させます（例: {"verdict":"NG","reason":"...","revised_prompt":"..."}）。スキーマに合わない出力は不正イベントとして扱い、遷移させません。プロトコルスタックで不正PDUを捨てるのと同じ考え方です。

3. ガード条件はコード側に置く
再試行回数、タイムアウト、累計コストの上限はモデルに任せず、状態機械のガードとして持ちます。「モデルが諦めない」ことで暴走するのを構造的に防げます。

4. 遷移ログを残す
「どの状態で、何を入力し、モデルが何を返し、どこへ遷移したか」を1行ずつ記録します。あとからその場の遷移図を再構成できるので、デバッグや再現もできます。

5. エージェントに丸投げするのは「探索」の場面だけ
試作段階で「とりあえず Claude Code に全部やらせてみる」のは、要件を探るのに有効です。そこで見えた流れを固定パイプラインと状態機械に落とし、本番はそちらで回します。プロトタイプはエージェント、本番は明示的な状態機械、という使い分けです。

まとめると、「ハーネス＝何でもモデル任せ」ではなく、ハーネスや状態機械が主導権を持ち、モデルは判定器・生成器として呼ばれる、という設計にすれば危なっかしさはかなり消えます。
